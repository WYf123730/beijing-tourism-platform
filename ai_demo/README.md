# AI 问答模块（RAG 最小实现）

在原平台数据之上加的一个问答入口：用户用自然语言提问，系统先从景点库检索资料，
再让大模型只依据这些资料作答。

不引入 LangChain、不引入向量库——目的是把 RAG 的每一环都摊开，能说清每个选择的原因。

## 链路

```
提问
 ├─ 检索：MySQL scenic 表 58 条景点 → 字面打分（景点名×4、正文命中×1、分类词表+3）
 ├─ 组装：命中资料套进固定模板，system prompt 约束「只依据资料，没有就说暂未收录」
 └─ 生成：调用大模型 API（OpenAI 兼容协议），返回答案 + 引用景点
```

## 运行

```bash
cd ai_demo
pip install pymysql          # 其余全是标准库

# 1) 不看模型，只看检索命中和将要发出的 Prompt（零成本，用来排查召回）
python rag_demo.py "故宫门票多少钱，几点开门" --dry

# 2) 正常问答
python rag_demo.py "故宫门票多少钱，几点开门"

# 3) 检索召回率评估（不调用模型，零 token）
python eval_retrieval.py
```

数据库连接复用 `后端/.env`；大模型 key 放在本目录 `.env`（已被 `.gitignore` 排除）。

## 实测结果

`eval_retrieval.py` 用 14 个问题测 recall@3：

| 类型 | 说明 | 命中 |
|---|---|---|
| 事实型 | 提问里有景点名（问门票、时间、位置） | 6/6 |
| 类别型 | 没有景点名，靠分类词表映射（问博物馆、长城、胡同） | 4/5 |
| 语义型 | 只有意图、没有关键词（想放松、想安静看书） | 2/3 |
| **合计** | | **12/14（86%）** |

## 已知局限（下一步要改的地方）

失败的两例都在语义层：

- 「带孩子去哪个公园合适」→ 召回天坛、北海、圆明园，漏掉北京动物园。因为"孩子"没有对应分类词
- 「想找个地方安静看一下午书」→ 只召回大栅栏一条，完全不相关

根本原因：**字面匹配只能匹配"字"，匹配不了"意思"**。分类词表是我手工补的一层补丁，
补得完常见场景，补不完长尾。

下一步：把景点简介向量化后存库，按语义相似度检索。切换后同样的评估集应当能把语义型
从 2/3 提到 3/3，而事实型不能退步——这是判断改造有没有成功的标准。

## 设计取舍

| 选择 | 原因 |
|---|---|
| 不用 LangChain | 一行 `RetrievalQA` 能跑通，但面试问「切分策略、召回不准怎么调」就答不上来；手写才能讲清每一环 |
| 一个景点 = 一段资料，不切分 | 简介只有 40–72 字，切分反而破坏语义完整性 |
| 先字面检索、后向量检索 | 有了基线才能证明向量检索确实更好，而不是"听说向量库更好" |
| system prompt 强制「查不到就说没有」 | 旅游场景编造景点门票、开放时间会直接误导用户，宁可拒答 |
| 温度 0.2 | 事实型问答要稳定复现，不需要创造性 |
